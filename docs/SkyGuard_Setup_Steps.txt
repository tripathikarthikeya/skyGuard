==========================
1. DATABASE
==========================

Goal: TimescaleDB reachable via one DATABASE_URL, decided by evidence,
not by default.

Step 1.1 - Benchmark first, before touching anything else
  - Time HistoryStore.get_recent() / trim() against the current CSV
    backend at:
      a) real station count (20)
      b) a stress-simulated count (200-500 fake stations)
  - This tells you whether migration is actually justified. Don't skip
    this step just because you already decided to use TimescaleDB -
    the number is what you'll cite as evidence later.

Step 1.2 - Sign up for Tiger Cloud (formerly Timescale)
  - Go to: console.cloud.timescale.com/signup
  - Create account (no credit card required to start)
  - Create a new service - pick the smallest/free tier
  - CONFIRM during signup whether this is a perpetual free tier or a
    time-limited free trial - check the pricing page before relying on
    it long-term

Step 1.3 - Get the connection string
  - Copy it from the console once the service is created
  - Format: postgresql://user:password@host:port/dbname

Step 1.4 - Store it safely
  - Put it in an environment variable: DATABASE_URL
  - NEVER hardcode it into config.py or any committed file
  - Add a .env.example file to the repo with a placeholder value, so
    judges know the variable exists without seeing real credentials

Step 1.5 - Enable the extension + create the schema
  - Use Tiger Cloud's built-in browser SQL editor (no local psql needed)
  - Run:

      CREATE EXTENSION IF NOT EXISTS timescaledb;

      CREATE TABLE sensor_readings (
          time              TIMESTAMPTZ NOT NULL,
          station_id        TEXT NOT NULL,
          temperature_c     DOUBLE PRECISION,
          pressure_hpa      DOUBLE PRECISION,
          humidity_pct      DOUBLE PRECISION,
          is_anomaly        BOOLEAN,
          fault_type        TEXT,
          severity          TEXT,
          anomaly_score_pct DOUBLE PRECISION,
          suggested_temperature_c DOUBLE PRECISION,
          suggested_pressure_hpa  DOUBLE PRECISION,
          suggested_humidity_pct  DOUBLE PRECISION,
          health_status     TEXT,
          source            TEXT NOT NULL,
          PRIMARY KEY (station_id, time)
      );

      SELECT create_hypertable('sensor_readings', 'time');
      SELECT add_retention_policy('sensor_readings', INTERVAL '30 days');

Step 1.6 - Rewrite history_store.py's internals only
  - Keep append() / get_recent() / get_all() / clear_source() /
    clear_all() method signatures EXACTLY as they are
  - state.py and main.py should need ZERO changes
  - trim() becomes a no-op / handled by the retention policy above

Step 1.7 - Async safety
  - state.py's ingest_reading() runs inside simulator.py's asyncio loop
  - Wrap DB calls: await asyncio.to_thread(...) if using psycopg2
  - Do not block the event loop with a raw synchronous call

Step 1.8 - Verify
  - Run the simulator, confirm rows land in sensor_readings
  - Confirm /api/trends and /api/history.csv still return correct data
  - Re-run the Step 1.1 benchmark against TimescaleDB, keep both
    numbers for the presentation


==========================
2. WEBSOCKETS
==========================

Goal: replace the 3-5s poll with a live push, and get a real,
quotable end-to-end latency number.

Step 2.1 - Add a WebSocket (or SSE) endpoint in main.py
  - e.g. /ws/live - accepts a connection, keeps it open
  - Alternative: Server-Sent Events (/api/stream) if you want something
    simpler than full WebSocket bidirectional handling - you only need
    server-to-client push here, SSE is enough and less code

Step 2.2 - Hook the push into the existing ingest path
  - In state.py's ingest_reading(), after the verdict is computed and
    written to history, broadcast it to any connected clients
  - Do NOT duplicate detection logic - this only pushes the verdict
    that already exists, nothing new is computed here

Step 2.3 - Frontend: replace the polling interval
  - Remove the setInterval/poll-every-3-5s logic
  - Connect to /ws/live (or /api/stream) once on page load
  - Update dashboard state directly when a message arrives

Step 2.4 - Add the visible latency readout
  - Timestamp the reading when simulator.py ingests it
  - Timestamp again when the frontend receives the push
  - Display the delta somewhere visible on the dashboard
    (e.g. "detection latency: 42ms")
  - This is a real number for your video/PPT - do not fake or round it
    misleadingly, use whatever it actually measures

Step 2.5 - Handle reconnects
  - If the WebSocket drops (mode switch, backend restart), the
    frontend should auto-reconnect, not silently go stale
  - Simple retry-with-backoff is enough, no need for anything fancier

Step 2.6 - Verify
  - Trigger an anomaly (replay / inject-anomaly) and confirm the
    dashboard updates without a manual refresh
  - Confirm the latency number looks sane (should be well under a
    second on a healthy connection)


==========================
3. DOCKER (deferred - do this last)
==========================

Goal: one docker-compose.yml that is BOTH the judge self-run bundle
AND (if Oracle VM is the hosting path) the actual production deploy.

Step 3.0 - Create requirements.txt FIRST (confirmed missing from repo)
  - Checked directly: there is no requirements.txt, requirements-dev.txt,
    or pyproject.toml anywhere in the current repo
  - Docker cannot install your dependencies without this - generate it
    from your actual working local environment:
      pip freeze > requirements.txt
  - Then manually trim it - pip freeze grabs everything installed,
    including unrelated packages you don't actually import. Keep only
    what main.py / model/*.py / history_store.py actually need
    (fastapi, uvicorn, pandas, numpy, scikit-learn, shap, joblib,
    requests, psycopg2-binary once Section 1 is done, etc.)
  - Commit this to the repo before writing the Dockerfile - it's also
    needed for a clean pip install even outside Docker

Step 3.1 - Disable native Postgres autostart (if not already done)
  - services.msc -> postgresql-x64-XX -> Startup type: Manual -> Stop

Step 3.2 - Install Docker Desktop
  - docker.com -> install -> launch -> wait for steady whale icon

Step 3.3 - Write docker-compose.yml (backend + db together)
  - Two services: your FastAPI backend (built from a Dockerfile) and
    timescale/timescaledb:latest-pg16
  - Backend's DATABASE_URL should point at the compose network's db
    hostname (e.g. "db", the service name), not "localhost", when
    both run inside compose together

Step 3.4 - Write the backend's Dockerfile
  - Base: python:3.11-slim (or whatever version the project actually
    targets - confirm from requirements.txt / runtime docs)
  - Install requirements.txt, copy source, expose the port, run with
    uvicorn main:app --host 0.0.0.0 --port $PORT

Step 3.5 - Start it
  - docker compose up -d
  - docker ps to confirm both containers are running

Step 3.6 - Enable the extension + schema (first run only)
  - docker exec -it <db-container-name> psql -U <user> -d <dbname>
  - Run the same CREATE EXTENSION + hypertable SQL from Section 1.5

Step 3.7 - Put this in the GitHub repo
  - docker-compose.yml + Dockerfile at repo root
  - README section: "Run locally: docker compose up -d - that's it"
  - This is your Practical Deployability evidence for judges who clone
    the repo instead of clicking the live link

Step 3.8 - IF Oracle VM is the final hosting path
  - Same docker-compose.yml runs on the VM directly
  - No separate "production config" needed - dev and prod parity by
    construction
  - Point the domain/IP at the VM, done

Step 3.9 - Verify
  - Fresh clone, fresh machine (or at least a fresh folder) -> docker
    compose up -d -> confirm it works with ZERO manual steps beyond
    that one command
  - This is the actual test of whether Practical Deployability holds -
    not "it works on my machine"
